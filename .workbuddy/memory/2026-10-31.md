## 安卓真机「捏合放大时所有条目都位移」：捏合路径缺 itemPinning

**现象**：双指捏合（0.333 → 0.500，列表小 → 列表大）时整屏条目一起上下漂；
点档位面板直接换档则只有共同可见条目位移、单侧条目原地淡入淡出。

**根因**（`lib/src/zoom_layout_utils.dart`）：`build()` 里有两条换档路径。
- 点击换档走 `_applyTargets(animate: true)`，里面调 `tracker.buildPinning(...)` 冻结
  "单侧可见条目"处置表，再作为 `metrics.itemPinning` 传下去 → 行为正确。
- 捏合换档走 `build()` 的 `pinch.isActive` 分支，`FolderZoomLayoutMetrics` **根本没传
  `itemPinning`（也没传 `transitionProgress`）** → `pinning == null` →
  `getGeometryForChildIndex` 全部走"各层加权平均"，于是每个条目都在两层几何之间插值位移。
  日志里 `[zoom][layout] mix ... layers=lx2/w0.49/e80.0,lx2/w0.51/e56.0` 每帧都在变，
  正是全体条目在动。

**修法**：新增 `_pinchPinning / _pinchPinningFrom / _pinchPinningTo / _pinchPinningReady`
+ `_resolvePinchPinning()`，在捏合分支里传入 `itemPinning` 与 `transitionProgress: t`。
- 缓存 key = (起始档位, 目标档位)；方向未定时返回 null。
- `mixLayers` 用 `_effectiveGeometryLayers(_curved.value)`（从点击动画中途接管时参照系正确）。
- `targetViewportTop` 用 `viewportTopForLayer(targetLayer)` 而非 `solveViewportTopFor`，
  与布局侧 `_layerViewportTop` 同口径，淡入条目在 `progress = 0` 处锁定值 == 目标值，起步不跳。
- 目标中途反转（双指间距跨过手势起点）时按新 key 重算：反转只可能发生在 `progress ≈ 0`，
  此时两层权重 (1, 0)，重算等价于按起始档位重新判定，不会瞬移。
- `_onPinchChanged` 里 `!pinch.isActive` 时 `_resetPinchPinning()`。

**测试**：新增 `test/zoom_pinch_single_side_fade_test.dart`，用真实双指手势驱动
`ZoomGestureLayer`（400×800、顶部 px=0），断言捏合中单侧条目原地不动（< 1.5px）且透明度变化、
共同可见条目仍位移。已验证：把 `itemPinning` 临时改回 null 时两条用例都失败。
全量 `flutter test` 23 项通过，`flutter analyze` 干净。

**顺带记**：`_sliverTopForPixels`、`_pinchTargetScale` 那套"目标只在方向确定后求解"的修复
（10-30 日志）已生效，本次日志里 `corr=0.0`、`px` 跟手，滚动补偿本身没问题。

## 确认缺陷：没适配「缩放列表上方还有别的 sliver」

**问题**：调用方在缩放列表上方放了 header（banner / SliverAppBar / tab bar）时，
列表起始位置不在视口顶端，插件把这种情况误判成"列表已贴顶"。

**根因**：`SliverConstraints.scrollOffset` 被 Flutter 钳在 0
（`viewport.dart:809 _sliverScrollOffset = scrollOffset <= 0 ? 0 : scrollOffset`）。
`SliverAnimatedZoomGridDelegate.getLayout` 直接拿它当 `viewportTop`，`viewportBottom`
用 `scrollOffset + remainingPaintExtent`，于是 viewportTop 少了 `precedingScrollExtent - pixels`。

实测（400×800，header 400 + SliverPadding 16，px=200）：
`scrollOffset=0 preceding=416 remainingPaint=584` → 插件算出 top=0 / vh=584，
真实是 top=-216 / vh=800。px=0 时 top 应 -416。

**后果**：
1. `_recordAnchor` 的 `viewportTop <= 0.5` 恒成立 → anchor 变 `top#0`，
   换档/捏合**完全不做滚动补偿**（日志 `skip: no scroll delta`，`targetPx == px`），
   退化成"首条目钉住、内容向下长"，焦点条目实测漂移 48px（无 header 基线只有 -23px）。
2. `_sliverTopForPixels` 在钳制区间里恒算错（真实 sliverTop 恒为 0），
   fling 中换档 / 捏合会把 pixels 拽回"上次布局时的像素"。
3. `vh = remainingPaintExtent` 而非视口高（584 vs 800），
   `maxScrollOffsetFor = extent - vh` 与真实 `maxScrollExtent` 差 216px
   （无 header 时只差 16px padding，所以一直被当成"可接受误差"）。
4. 吸顶 header 时 `constraints.overlap`（实测 56 / 400）从未被使用，焦点仍取屏幕中心。

**没坏的区间**：只要 header 被滚出视口（pixels > preceding），mid/bottom 换档、
贴底、焦点锚定全部精确（已实测 none / scrolling / pinned × mid / bottom）。

**修复（已实施，v0.0.4）**：
- `getLayout`：`leadingGap = max(0, viewportMainAxisExtent - remainingPaintExtent)`；
  `viewportTop = scrollOffset - leadingGap`；`viewportBottom = viewportTop + viewportMainAxisExtent`。
  → 实测 px=200/header400：top 从 0 变成 -216，vh 从 584 变成 800。
- tracker 新增 `precede`（= `pixels - viewportTop`，每次布局刷新）、`minViewportTop = -precede`、
  `atScrollStart`（`pixelsAtLayout <= 0.5`）。
- `_recordAnchor`：贴顶判据换成 `atScrollStart`；焦点加 `max(focus, -viewportTop)` 兜底
  （焦点上方没内容时才退化成顶对齐）。
- `_resolveFocusY`：`topBlend` 在 `viewportTop < 0` 时直接归 0 —— 否则"距顶一屏压焦点"
  在 header 场景会把焦点压到列表首行，等价于不补偿。**这是本次最隐蔽的一处**：
  只改坐标系时新测试仍然全绿但 pixels 仍不动，就是它压着。
- `_anchorTopIn(top)` 返回 `anchorSourceTop`（钉住当前位置）而非 0；
  `viewportTopForLayer` 下界从 `0` 改成 `minViewportTop`。
- 未做：`overlap`（吸顶条第 56px 被遮挡）仍未扣减，焦点仍取屏幕中心，误差约 overlap/2。

**效果实测（header 400，list→largeList）**：
| px | 修复前 | 修复后 |
|---|---|---|
| 100 | 焦点条目 396→420，pixels 不动 | 396→395，pixels 100→125 |
| 200 | 376→424，pixels 不动 | 376→369，pixels 200→254.7 |
| 340 | 396→492，pixels 不动 | 396→395，pixels 340→437 |

**测试**：新增 `test/zoom_header_offset_test.dart`（9 例：可滚走 header × px 100/200/340、
页面顶端、贴底、吸顶 header 中段/贴底、header 下捏合、无 header 基准）。
已验证修复前这 4 个关键用例失败（`pixels` 原地不动），修复后全绿。
全量 `flutter test` 32 项通过，`flutter analyze` 干净；example 里加了一块 header 便于真机验证。

## 贴底后「捏合换档」比「点击换档」少滚一截（内容整体偏下）

**现象**（用户报）：先滚到列表底部，再用双指手势换档，动画怪、焦点明显偏下；
直接点档位图标则正常。

**根因**：`_onPinchChanged` 求解目标像素时又按上界夹了一次：
`clamp(0, viewportTracker.maxScrollOffsetFor(targetLayer))`。
`maxScrollOffsetFor` 返回的是 **sliver 坐标**（`contentExtentIn - viewportHeight`，且
`contentExtentIn` 不含外层 `SliverPadding` 的前后 padding），而 `_pinchTargetPixels` 是
**滚动像素**。两者差 `precede`（上方 padding / header）+ 尾部 padding。只有"贴底"会露馅：
点击路径（`_applyTargets`）压根不夹上界，精确贴底；捏合被夹短 `precede + 尾部padding`。

**实测差量**（400×800，StandardList → LargeList / LargeGrid → MediumGrid，两个方向一致）：
- 无 header：点击 11712 / 捏合 11680 → 少 32px（末尾 16px 被切）
- header 400：点击 12112 / 捏合 11680 → 少 432px（= 400 + 32），这就是"焦点明显偏下"

**修法**：删掉上界夹取，只保留 `max(0, ...)`，与点击路径完全同款（越界交给本次布局的
`applyContentDimensions` 纠正）。`lib/src/zoom_layout_utils.dart` 约 1983 行。
注释里写清了"为什么不能按 `maxScrollOffsetFor` 夹像素值"，避免以后又被加回去。

**测试**：`test/zoom_bottom_pinch_matches_tap_test.dart`（4 例：header 0 / 400 × 放大 / 缩小）。
同一布局跑两条路径，断言最终 `pixels`、`maxScrollExtent`、每个可见条目的 top 都对齐（1px 内）。
已验证修复前 4 例全失败（报"少滚了 32 / 432px"），修复后全绿；全量 36 项通过，analyze 干净。

## 支持「一页多个缩放网格」（目录列表 → 固定高介绍行 → 文件列表）

**需求**：一个页面里上下两个列表都参与缩放，换档时两个一起动、动画不乱。

**为什么原来不行**：`FolderZoomViewportTracker` 是单 sliver 的，两个 delegate 在同一帧各自
`record()` 会互相覆盖 `viewportTop / precede / contentCount`；`_layerViewportTop` 只有一份，
下游网格的条目按上游坐标系摆放（过渡期整片偏移 `precede_B`）；`_applyTargets` 只补偿锚定
列表自己的几何变化，漏掉上游高度变化 `ΔH` —— 实测换档瞬间下面列表被顶走 336px。
单侧淡入淡出的冻结表也是全局一张、按 index 索引，两段会互相顶替。

**方案**：单 builder + 多 section，全部换算搬到**页面坐标**。
- `SliverAnimatedZoomGridDelegate(section: id)` / `ZoomItemScaffold(section: id)`，
  `section` 留空 = 单列表老路径（完全向后兼容）。
- tracker 内 `_ZoomSectionState` 记 `precede / gapBefore / contentCount / 间距 / 锚点`。
- `gapBefore_k = precede_k − Σ_{j<k} H_j`（反推，缩放无关 → 介绍行固定高即可复用）。
- `targetPixels = pageStart_anchor(L) + localTargetTop(L)`；贴底 = `pageEnd(L) + tail − vh`；
  贴顶 = `pixels`。
- `viewportTopForLayer(layer, section:)` 返回**段局部**值；`correction` 是页面级残差。
- pinning 按段各冻结一份（`metrics.sectionPinning` + `pinningFor(section)`）。
- section 淘汰用「布局轮次」判定（同一段一轮里出现两次 = 新一轮），不依赖 build 次数。

**坑**：`_resolveFocusY` 的「距顶一屏压焦点」用的是段局部 `viewportTop`，段在页面中段时
会误判成「贴近顶部」退化成顶对齐 —— 这是既有行为（单列表同理），不是 bug，写测试时踩过。

**测试**：`test/zoom_multi_section_test.dart`（5 例）。去掉上游补偿后 5 例中 2 例失败，
确认能守住回归。全量 48 项通过，analyze 干净。示例见 `example/lib/multi_list_page.dart`。

## 修多列表三个现象（下游列表滚到中段换档时暴露）

现象：①第二个列表中部换档焦点位置不对 ②在"网格小 ↔ 网格"之间反复切换，页面一路下移到
底部 ③第二个列表中部换档没有淡入淡出，条目直接闪现。三者同一个根因 + 三个独立缺陷。

**根因（最要命）**：段的存活判定用"同一个段在一轮布局里出现两次 = 新一轮开始"来推轮次，
但同一个 sliver 一帧里本来就会被 `getLayout` 调用多次（日志实测每帧 dirs, files, files），
于是把还活着的 dirs 判成已移除 → `gapBefore` 被重算成 `precede` 本身（284 → 696）→
下游段的上游高度补偿（412px）整段丢失。改法：用
`SchedulerBinding.instance.currentFrameTimeStamp` 当帧标识（同帧内恒定、与 build 次数无关），
留 `kSectionFrameGrace = 2` 帧宽限；并注意**先推进帧号/淘汰、再创建新段**，否则新段
`frameIndex = 0` 会被同一轮清理顺手删掉（连带条目数丢失）。

**漂移**：锚每次稳点都按"焦点所在行的第一个条目"重取（40 → 36），而同一索引在 6 列/8 列下
属于不同的行，一来一回净丢一行 → 几十次后滑到底。改法：锚条目**粘滞** —— 上一次的索引
只要仍与焦点同行（`_geomIn` 的 `scrollOffset` 相等）就继续用它。实测 4 组档位对
（small↔medium、medium↔large、standard↔small、compact↔large）来回 3 轮，最终 px 与起始
完全相等。

**焦点位置不对**：`_resolveFocusY` 的"距顶一屏压焦点"用的是**段局部** `viewportTop`，第二段
在页面中段时局部值只有几百，被误判成"贴顶"，焦点从 400 被压到 347/363。改成页面坐标
（`px`），但保留 `sectionTop < 0 → 不渐变`（页头还在视口里时必须走条目锚定，
`test/zoom_header_offset_test.dart` 守着这条）。

**淡入淡出消失**：冻结表的 `targetViewportTop` 也来自被污染的页面模型，单侧可见的条目被判成
"两侧都可见"→ 不淡不闪。上游补偿恢复后自然正确；新增用例不仅断言
`sectionPinning` 非空、不透明度逐帧连续，还断言被冻结条目**真的在视口里**。

**其他连带**：①`gapBefore` 只在稳态（单层几何）刷新，过渡期高度是插值值反推会带偏；
②锚点/贴底判据改用 `px - precede` 现场换算，不用可能残留上一帧混合值的 `viewportTop`；
③`_refreshGapBefore` 的 `gapReady` 仍是"上游条目数未知就不补偿"的兜底。

测试：`test/zoom_multi_section_test.dart` 7 例，全量 50 项通过，`flutter analyze` 干净。

## 两段网格之间那块固定高内容，换档时不跟着动（原地消失 / 出现）

**现象**（用户报）：一页两个列表、中间夹一块固定高内容；滚到"第一段末尾在顶部只剩半行"
的位置再换档，中间那块内容的**位移动画消失**——第一帧整体偏一截，然后整段过渡钉住不动。
竖屏更明显（末帧还会甩一下）。

**根因**（`lib/src/zoom_layout_utils.dart`，`_SliverAnimatedZoomGridLayout.getGeometryForChildIndex`）：
单侧可见条目（`FolderZoomItemPin.fadeIn/fadeOut`）的位置是锁在**屏幕**上的：
`scrollOffset = viewportTop + 冻结的屏幕 y`，`viewportTop = pixels - precede`。

而 `RenderSliverGrid.performLayout` 上报的 `scrollExtent` / `paintExtent` 取自
"已布局子条目里最靠下那条的下边缘"（`reachedEnd` 时直接 `trailingScrollOffset`）。
锁定坐标跟着滚动走 → 本段高度 = `(pixels - precede) + 常数`。
视口里**后面每个 sliver 的位置都是前一个 extent 累加**（`layoutOffset += layoutExtent`，
`layoutExtent` 默认 = `paintExtent`），所以本段之后的内容被摆到**屏幕常量**上：不跟着插值走、
第一帧又偏一截 = "原地突然消失 / 出现"。

**触发条件**：本段**变矮**（列表→网格）+ 末尾几行有单侧可见条目。淡入条目锁在目标档屏幕位置、
高度也是目标档的（194 vs 插值末端 80），它的下边缘恰好等于**最终**内容末端 → 全程压过插值末端 →
间隔行位置恒定。实测（1200×800，px 1122→347）：intro 30 → 96.8（第一帧）+66.8px 然后冻结；
竖屏单帧 238px。反方向（网格→列表、段变长）不复现——几何末端本来就压得住。

**修法**：`_clampPinned(offset, extent)` 把锁定条目的 sliver 坐标夹进
`[0, 本段插值内容末端 - 条目高度]`（末端用 `tracker.contentCountOf(section)` + 各层
加权 `_maxScrollOffsetIn`，与 `computeMaxScrollOffset` 同口径）。锁定失效的部分只有几十像素、
且只发生在正在淡入/淡出的条目上。
- **试过但没用**：①只把 `getMaxChildIndexForScrollOffset` 夹回 `childCount-1`（让
  `reachedEnd == false` 从而改用 `computeMaxScrollOffset`）—— `scrollExtent` 确实变对了，
  但 `paintExtent` 仍是子条目下边缘算出来的，间隔行位置完全不变。②临时关掉 `pinning`
  作为对照：确实恢复平滑，证明 pin 几何是唯一原因。

**测试**：新增 `test/zoom_gap_motion_test.dart`（横屏半行位置 / 竖屏 / 第二段同向移动，3 例），
断言位移摊在整段过渡里（任何一帧 ≤ 总位移 1/3、第一帧后未到终点）。未修复时 2 例失败
（报"一帧走了 66.8px" / "末帧 -238.2px"）。全量 55 项通过，analyze 干净。

## 「第二个列表整段在屏幕外时缩小档位」动画乱（下面的元素被顶到上面来）

**现象**（用户报）：一页两个列表 + 中间分段，屏幕内只见第一个列表与分段，第二个列表在
折叠线下。缩小档位时第一个列表变矮、第二个列表上移，此时第二个列表的动画乱 ——
表现为"下面的元素在动画期间移到上面来"。

**根因 A（主因，`buildPinning` + `_clampPinned` 下界）**：条目锁定位置是**屏幕坐标**，
布局侧换算成 `scrollOffset = viewportTop + 锁定y`。第二段起始边还在视口顶端之下时
`viewportTop < 0`（实测 -798），淡入条目的锁定 y（773.8）小于 `-viewportTop` →
偏移为负 → 条目不能画在本段起始边之上 → `_clampPinned` 的下界 0 把它夹回段首。
结果：整段被冻结的条目**骑在本段起始边上跟着上移**，等起始边越过它原本的锁定位置时
再一帧弹回去。实测第 0 帧就给 `files` 段冻结了 0..15（两行 8 列），全部夹到 0 →
两行叠在分段底边同一处再各自弹开。（下界 0 是上一个 fix「段间那块固定高内容不动」
加的，它解决了 extent 污染，但顺带制造了这个反向症状。）

**根因 B（叠加，`getLayout` 的 `leadingGap` 饱和）**：
`leadingGap = max(0, viewportMainAxisExtent - remainingPaintExtent)` 只在
`remainingPaintExtent > 0` 时成立。起始边落到视口**底端之下**（整段还没进屏幕）时父级把
`remainingPaintExtent` 夹成 0 → 反推恒等于视口高 → `precede` 少算"离折叠线的距离"
（实测 16px = 外层 padding，缓存范围内可到几百 px）→ `gapBefore`/`pageStart` 偏小 →
这一段过渡期整体偏高、末帧回弹十几像素。

**修法**（`lib/src/zoom_layout_utils.dart` 两处）：
1. `buildPinning`：`lockedTop + s.viewportTop < -eps` 时不冻结，退回 `shared`
   （让这一段跟着几何整体上移）。判据用起始帧的 `s.viewportTop`，只对淡入条目生效。
2. `getLayout`：`remainingPaintExtent > 0` 时保持旧式；否则用
   `pixels - constraints.precedingScrollExtent`（`RenderSliverPadding` 会把
   `beforePadding` 加进原值，见 `sliver_padding.dart:143`，与 `pixels` 同坐标系）。

**测试**：新增 `test/zoom_second_section_offscreen_test.dart`：断言换档全程
`sectionPinning['files']` 为空、任一条目都不跑到分段之上、逐帧单调上移、
末帧与稳态差 < 1px。未修复时第 0 帧就报"冻结了 0..15"。全量 57 项通过，analyze 干净。

**顺带记**：这一段"整体上移"本身是设计使然（锚只在焦点所在段，焦点以下的内容按
"焦点到它之间缩了多少"上移），不是 bug；本次修的是逐条错位/叠在一起/末帧弹一下。
