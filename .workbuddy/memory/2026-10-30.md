## zoomable_sliver_grid 换档滚动锚定：改为焦点锚定（0.0.1 → 0.0.2）

**问题诊断（已确认）**
- `Scrollable.maybeOf(context)` 在 `FolderZoomSliverBuilder` 的 context 上恒为 `null`
  （builder 在 `CustomScrollView` 之上，maybeOf 只查祖先）→ 滚动补偿从未执行，
  顶部因为 offset=0 恰好正常，中段/底部换档纯跳变。
- tracker 只处理顶边界（`viewportTop <= 0`），没有底边界；`viewportTopForLayer` 只有下界夹取，
  真被 `maxScrollExtent` 夹住时假想视口与真实视口差 2800+ px → 可见性判断全错 → 整屏空白帧。
- 过渡期"单侧可见"条目走 `scrollOffset + delta` 钉住写法，叠加上述问题 = 画面冻住再整屏跳。

**方案（用户已确认）**
- 不变量改成"焦点处的内容不动"：`c = vTop + f; i, r = indexAt(c), (c-oA(i))/strideA;
  targetTop = oB(i) + r*strideB - f`。与顶部锚定只差 `r*(strideB-strideA)`。
- `r` 用**槽位步距**（条目高度+行间距）为分母，否则焦点落在行间空隙时被压到 1.0，凭空多/少一行。
- 焦点：默认视口中心；捏合取双指中点；距顶/底不足一屏时把 f 渐变到 0/视口底（两端退化顶/底对齐）。
- 贴边（±0.5px）直接记成 top/bottom 锚；底部用两端内容总高之差平移，避开 SliverPadding 的坐标偏差。
- 过渡期把 `correction = 真实vTop - 假想vTop`（按层权重）加到各层视口顶部，可见性判断与屏幕一致。
- 滚动与布局共用同一个 eased 值，多档跳转直接从起点解到终点，不做逐档累加。

**落地**
- `FolderZoomSliverBuilder` 新增可选 `controller`；未传时用 `RenderViewportBase.offset` 从渲染树自动发现。
- `FolderZoomViewportTracker` 重写（焦点锚 + 边界 + contentCount + spacings + correction）。
- `_SliverAnimatedZoomGridLayout.contentExtentIn` 由 `_maxScrollOffsetIn` 抽出为静态；`computeMaxScrollOffset` 回填 childCount。
- pinch：`FolderZoomPinchController.focalGlobal`，手势层传双指中点，捏合开始时 `refreshAnchor`。
- 新增 `test/zoom_anchor_test.dart`（10 条：顶/中/底 × 双向、贴底精度、空白帧、无 controller 兜底、捏合）。
- 顺手修了 `example/test/widget_test.dart` 引用不存在的 `MyApp`；README/CHANGELOG 补焦点锚说明。

**验证**：`flutter analyze` 干净；`flutter test` 10 passed；example 冒烟测试通过。

## 触底换档「条目从下往上弹一下」（0.0.2 → 0.0.3）

用户报：滚到底部再放大档位，几乎所有条目快速从下往上弹一下。用逐帧探针（记录每条目
`tester.getRect().top`）实测出四个独立成因，都在 `lib/src/zoom_layout_utils.dart`：

1. **几何按布尔可见性分支**（主因）：`getGeometryForChildIndex` 里"两层都可见→加权混合，
   只有一层可见→`geom.scrollOffset + (viewportTop - layerViewTop)` 锁死到该层屏幕位置"。
   过渡期滚动要平移几千像素，条目会反复翻转可见性，每翻一次就在混合值与层锁定值之间瞬移。
   探针实测 item 107 逐帧 `51 → -18 → 280 → 527 → 366`、item 112 `-240 → 156 → -259`。
   改为**纯几何加权**：`paintTop = Σw·(o_L - layerTop_L) - correction`，对 progress 连续。
2. **`_onTick` 用上一帧的 `maxScrollExtent` 夹取**插值位置。触底换档内容每帧长上千像素，
   滚动永远慢一帧 → 条目被画低上千像素再被拽回。删掉夹取，越界交给
   `applyContentDimensions`（`jumpTo` 越界不会被立即夹取，会走回弹模拟，很丑，别再依赖它）。
3. **终帧补偿丢失**：`AnimationController` 最后一 tick 先 `stop()` 再 `notifyListeners()`，
   `isAnimating` 已 false。改成 `addStatusListener` 在 `completed` 里补最后一帧
   （原来触底会停在离底部 ~13px，且残差随帧率变化）。
4. **过渡中再次换档目标算高**：`_startSliverOffset` 取 tracker 里上次布局的 `viewportTop`，
   `_startScrollPixels` 取当前 `position.pixels`，差一整帧。新增
   `FolderZoomViewportTracker.pixelsAtLayout` + `scrollPixelsReader` 回调（build 期由
   state 注入 `_scrollPosition()?.pixels`），用 `_sliverTopForPixels()` 对齐到同一时刻。
   连点两档曾多算 290px。pinch 路径同样改用该 helper。

**连带删除**：单侧可见条目的原地淡入淡出（`resolveItemTransition` 现恒返回 `isShared: true`）。
`kFolderZoomFadeScaleDelta` 标 `@Deprecated`，`isGeometryVisibleInViewport` 已删。
`zoom_item_scaffold.dart` 里 `isFadeScale` 分支保留为死路径未动。

**新增回归测试** `test/zoom_transition_motion_test.dart`：断言过渡期每个条目屏幕位置**单调**
（不允许中途折返，方向按自身净位移判定——触底时方向取决于内容总高变大还是变小，与放大缩小无关）。
覆盖竖屏/横屏触底放大、触底缩小、中段、连点两档。`flutter test` 15 passed，analyze 干净。

**遗留**：Vynody 仓库内还有一份同源代码 `lib/widgets/folder_layout_utils.dart`（2086 行），
带同样的四处问题，且其 `test/widgets/folder_zoom_geometry_trajectory_test.dart` 断言了旧淡入淡出行为。
若要 App 也修，需同步移植并改写那批断言。已告知用户，未擅自改动。

## 安卓真机「换档时列表快速上下移动」：捏合目标求解修复 + 插桩

**已确认的确定性 bug（捏合路径）**：`startPinch()` 自己会 `notifyListeners()` 一次，
此时 `updatePinch()` 还没跑过，`targetZoomScale == baseZoomScale`。早期实现把目标滚动
位置在这一帧就定死（`targetTop == 起点`），整段捏合期间 `pixels` 一动不动，而几何层
已向目标档位插值 → 条目被甩出上千像素。修法：
- 新增 `_pinchTargetScale`，只在 `targetZoomScale` 变化时重算目标（并支持中途反向重算）。
- 目标夹取用 `maxScrollOffsetFor(targetLayer)` 而非当前 `position.maxScrollExtent`
  （过渡期内容总高每帧在变，旧值会把缩小方向的目标提前截断）。
- 回归测试 `test/zoom_anchor_test.dart`「捏合放大：全程跟手…」，旧代码下会失败。

**插桩（用户要求在代码里打日志，他自己跑真机）**：新增 `lib/src/zoom_debug.dart`
- `folderZoomDebugLog`（默认 `!kReleaseMode`，已从包入口 export）、`zoomLog(channel, msg)`、`zd()`。
- 频道：`env`（平台/尺寸/dpr/textScale）、`pos`（ScrollPosition 解析来源与变化）、
  `didUpdate`（scale 变化 → animate 与否）、`switch`（过渡起点全量快照：px/sliver/targetPx/
  maxCur/maxTarget/anchor/physics）、`tick`（每帧 t/ms/want/px/jump/EXTERNAL drift/max/top）、
  `layout`（tracker.record 的 top/assumed/corr/maxMix/layers）、`layers`（动画中却只剩一层的 WARN）、
  `touch`/`pinchCtl`/`commit`/`step`（手势与档位结算链路）。
- `EXTERNAL drift=` 是关键判据：两帧之间滚动位置被别处改过（边界修正/弹道/拖动）就会打出来，
  安卓 ClampingScrollPhysics 与 macOS BouncingScrollPhysics 的差异会在这里显形。

## 真机日志到手：确认真机上存在两个 ScrollPosition（幽灵位置）

`example/run.log`（安卓 393.8×750.2 + AppBar，120 条）证据链：

1. `switch` 同一行里 `px=0.0` 而 `top=5251.8`。同一时刻同一 ScrollPosition 不可能既 0 又 5251
   ⇒ `_scrollPosition()` 拿到的位置不是布局本 sliver 的那个。
2. `precede = pixels - constraints.scrollOffset = -4662.5`，而前置滚动内容长度必然 ≥ 0。
3. `px` 只在被我们 `jumpTo` 时变化（0 → 1688.1 → 0 → 863.3 → 341.3 → 4480），用户滚动完全不体现。
4. `top` 只在换档时变（5251.8 → 4055.7 → 3669.1 → 4397.0 → 6908.0），随内容总高变化 —— 真实位置
   被夹在底部，说明列表其实是滚到底的，只是我们够不着它。
5. 捏合段同样：`top=6908.0` 全程冻结，`px` 从 4480 平滑走到 3815。

**可见症状成因**：滚动补偿打在幽灵位置 ⇒ 真实视口不动，而几何层的假想视口跟着 `px` 走 ⇒
`correction = 真实top - 假想top` 把内容整段顶走；过渡结束 `correction` 归零 ⇒ 内容弹回。
第二次换档更狠：`startSliver` 用真实 top、`px` 用幽灵值，算出 `targetPx = -1836.0`，
clamp 到 0，直接把列表送到顶部 = 用户看到的"快速且明显的上下移动"。

**本地复刻**：`test/scratch_example_repro_test.dart` 完全照 example 结构（Scaffold+AppBar+
LayoutBuilder+ZoomGestureLayer+CustomScrollView，不传 controller）搭，结果干净：
`viewports=1`、`precede=16.0` 恒定、`px` 与 `point` 同步。⇒ 不是纯代码路径问题，是运行时状态差异。

**已做的加固**（`zoom_layout_utils.dart`）
- `_findViewportPosition` → `_collectViewportPositions`：返回**全部**候选而不是第一个。
- `_selectAligned`：用 `pixels - viewportTop >= 0` 过滤 + 取最小前置长度来挑，替换"盲取 DFS 第一个"。
- `_isAlignedWithLayout` + `_validatedPosition` + `_selfHealBudget(3)`：缓存位置与布局对不上时丢弃重挑，
  带预算避免每帧遍历渲染树。
- 新增日志频道：`find`（子树里所有 viewport 的 vp#/pos#/px/max）、`select`（候选与选择结果）、
  `align`（`precede = px - top` 及其变化，**不变量一旦变化就是挑错位置的铁证**）。
- `switch` 行补充 `root=`、`posId=`、`precede=`。

**待确认**：需要真机再跑一次看 `find/select/align`。两种可能：
- `viewports=2` ⇒ 幽灵确实在子树里，`_selectAligned` 已能挑对（本轮可能已修好）。
- `viewports=1` 且 precede 仍为负 ⇒ 真实 viewport 不在 builder 子树里，另需换定位手段。



## 恢复「单侧可见条目原地淡入淡出」（分类改为过渡开始时冻结）

**问题**：`3cc4109 修复触底换档"从下往上弹一下"` 为了消除弹跳，把 `resolveItemTransition`
改成恒返回 `isShared: true`，单侧可见条目的原地淡入淡出被整块删掉 ⇒ 所有条目都走加权位移，
只在一侧可见的条目从很远的地方飞进 / 飞出，与需求（两侧都可见才做位移动画）不符。

**真正的病因**：不是"分类"错了，而是**分类逐帧重算**。可见性是布尔量，过渡期滚动位置要平移
几千像素，条目反复翻转可见性，每翻一次位置就在"混合值"与"层锁定值"之间瞬移。

**修法**：保留分类，但把它**冻结**。
- 新增 `FolderZoomItemPin { shared, fadeOut, fadeIn }` + `FolderZoomItemPinning`
  （若干 `_PinSegment`：连续索引段 + 冻结的屏幕 top + 所属档位层 + 起始不透明度）。
- `FolderZoomViewportTracker.buildPinning(...)` 在 `_applyTargets(animate: true)` 里调用一次，
  输入是**折叠后的 `_geometryFrom`**（= 上一帧屏幕上实际生效的混合层）+ 目标层 +
  `solveViewportTopFor(targetLayer)`。判定两侧可见性；两侧都可见 → shared，只在一侧 → fadeOut/fadeIn。
  只为 `[lo,hi]`（各层视口 ±一两屏）算几何，不整表扫。
- 布局侧 `getGeometryForChildIndex`：fadeOut 锁 `viewportTop + 冻结top`（用 dominant 源层取尺寸）；
  fadeIn 锁目标位置（`lerp(冻结top, 当前目标top, progress)`，正常换档时是恒等映射，
  只有连点两档目标变了才需要收敛，避免终帧跳一下）。
- `resolveItemTransition`：`opacity = lerp(segment.opacityFrom, 终点, progress)`，
  `scale = 1 - 0.15*(1-opacity)`；`kFolderZoomFadeScaleDelta` 去掉 `@Deprecated`。
- 连点两档：`_controller.isAnimating` 时把旧表作为 `previous` 传入，已锁定条目沿用**上一帧真实
  画出来的位置**与当时的不透明度（`opacityFrom` 接续），否则会从锁定位置瞬移到混合位置（实测 126px）。
- `getMin/MaxChildIndexForScrollOffset` 一并覆盖 `firstPinnedIndex/lastPinnedIndex`，
  否则锁定条目会因为"算出来在视口外"而不被构建。

**测试**：新增 `test/zoom_single_side_fade_test.dart`（20 passed，analyze 干净）
- 列表→网格（400×800 下 LargeGrid 是 2 列大卡，比列表**稀**）：fadeOut 条目整段过渡位置不变、
  不透明度递减；网格→列表：fadeIn 同理。
- 直接读渲染树里的 `Opacity`，确认 `zoom_item_scaffold` 的 `isFadeScale` 分支真的生效
  （它此前是死代码）。注意控件树停在**最后一帧**，对照要用最后一个 sample 的 metrics。
- 连点两档：锁定条目逐帧位移 < 4px。
- 原有 `zoom_transition_motion_test.dart` 的单调性断言仍然通过（锁定条目净位移 0 会被跳过）。

**踩坑**：`expect(isNotNull)` 之后再取 `pinning!.firstPinnedIndex!` 要用 `!`，否则 `int?` 报错。

## 安卓换档"所有条目都位移"根因：ScrollPosition 被换掉后缓存成僵尸
- 现象：macOS 正常，安卓上换档时**全部条目**跟着几何层滑动，而不是"只有共同可见条目位移、
  其余原地淡入淡出"。链路一律是"滚到列表中间 → 切小列表 → 切大列表"。
- 抓法：比 `[zoom][switch]` 的 px / startSliver / targetPx。macOS `px=5642 startSliver=5626
  targetPx=3851`；安卓 `px=0.0 startSliver=4121.7 targetPx=-1349`（负值被 `math.max(0,..)` 夹成 0）。
  `[zoom][tick]` 全程 `clamped=0.0 jump=no`，`[zoom][layout]` 的 `top` 停在 4121.7 不动、
  `assumed` 一路下掉靠 `corr` 掩盖 —— 滚动补偿一次都没生效。
- 根因：`Scrollable.didChangeDependencies()` 无条件 `_updatePosition()`（flutter/scrollable.dart:673），
  旧 ScrollPosition 被 `scheduleMicrotask(dispose)`，新位置顶上；**两者共用同一个 ScrollContext**，
  旧位置 `pixels` 冻结（这里就是 0.0）且 `mounted` 仍为 true。安卓启动后 MediaQuery（系统栏/刘海
  insets）还会再变一次触发这次替换；macOS 窗口尺寸一帧稳定，所以只有安卓中招。
- 库里的洞：`_scrollPosition()` 用 `identical(cached, _validatedPosition)` 短路，首帧校验通过后
  **永远跳过校验**，缓存里那个僵尸位置整场会话都在用。
- 修法（lib/src/zoom_layout_utils.dart）：缓存 viewport 本身（`_cachedViewport`），每帧用
  `identical(viewport.offset, position)` 做 O(1) 存活校验；去掉 `_validatedPosition` 短路；
  `_collectViewportPositions` 改成 `_collectViewports` 返回 `List<RenderViewportBase>`，
  `_selectAligned` 也返回 viewport；heal 成功时把 `_selfHealBudget` 复位成 3。
- 验证：新增 `test/zoom_stale_position_test.dart`（改 MediaQuery 的 gestureSettings 强制换位置，
  断言换档全程焦点条目位移 < 40px 且 pixels 变化 > 500）。把修复临时回退后该测试失败
  （item-48 直接消失），恢复后 21 个测试全过。
- 临时规避：给 `FolderZoomSliverBuilder` 显式传 `controller`（走 `controller.position`，不碰渲染树路径）。
